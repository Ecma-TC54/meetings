## Key discussion

### Announcements - Automotive threat modelling

There has been an effort within the automotive industry to develop a specification to represent risk information. The relevant groups have now decided instead to align with the committee’s work. In conjunction with the automotive and medical device industries, OWASP has spun up a new working group for products security and risk. Meetings will begin in September and details will be made available on the OWASP software supply chain calendar.

### Calls for consensus for normative changes to CycloneDX 2.0

#### [CycloneDX 2.0 Threat Modeling Branch: Review Guide for Ecma TC54](https://github.com/Ecma-TC54/meetings/issues/9)

This change was inspired by Open Threat Model (spearheaded by Irius Risk), which TC54 began reviewing in 2025. The goal was interoperability between threat modeling tools, which can encourage regular review and update of risk assessments. The content was intended to provide method-agnostic threat modeling, and was supported by creators of several well-known methods.

The committee reached consensus to merge this change.

#### [CycloneDX 2.0 Service Components](https://github.com/CycloneDX/specification/pull/975)

This change moves services into being a component type. This is possible thanks to the decision to drop XML support, as JSON Schema permits conditional data. Information regarding the relationships between services has been moved in to the blueprint portion of the threat modelling branch which was just approved.

The committee reached consensus to merge this change.

#### [CycloneDX 2.0 Unified Evidence Model](https://github.com/CycloneDX/specification/pull/980)

This change primarily provides a refactor, with some changes to support a unified evidence model. For example, copyright is no longer its own independent object, but rather a part of the broader evidence. Additionally, these changes provide for a data model that makes VEX a more usable documentation format tool for common organisations.

The committee reached consensus to merge this change.

#### [CycloneDX 2.0 First-Class ~~Hardware~~ Physical Support](https://github.com/CycloneDX/specification/pull/982)

This change has two main purposes, to be able to describe certifications and traceable sources for hardware components. Certifications—previously hard to scale due to breadth—now have specific fields for name, level, attestation, and more. They can be applied to components as well as to organisations.

Hardware traceability is beneficial for any hardware manufacturers, and doubly so for those who wish to reach the US market after a recent executive order. Much of the schema description has been inspired by a recent CISA guide. Some fields, such as lead time, may not be appropriate for finalised SBOMs, but since CycloneDX is also an API specification, they’re important in that context.

There was a conversation about component origin distribution—the committee decided to use the term “shall” in the context “The percentage of all entries shall total 100, within rounding of the stated precision”.

The committee reached consensus to merge this change.

#### [CycloneDX 2.0 Component and Crypto Agility](https://github.com/CycloneDX/specification/pull/947)

This change introduces cryptographic agility including how keys are rotated and renewed to support for clear and complete CBOMs.

The committee reached consensus to merge this change.

#### [CycloneDX 2.0 Output Length of Cryptographic Algorithm](https://github.com/CycloneDX/specification/pull/931)

This PR was not ready for review.

### Task Group updates

#### Update from TC54-TG1 (Pavel Shukhman)

TG1 is working on an auth endpoint for TEA which will provide auth for all other TEA endpoints. Additionally, an endpoint for downloading raw artifacts is being added.

#### Update from TC54-TG2 (Michael Herzog)

There are no normative changes happening with PURL right now as the document is being reviewed for editorial clarity and consistency before being prepared for the Ecma GA and ISO-IEC/JTC 1 submission. There will be two informative annexes added, including qualifier keys, which may be normative in a future edition.

VERS first edition is being prepared for submission as well, including low-level document formatting choices such as converting from Markdown HTML or ecmarkup.
